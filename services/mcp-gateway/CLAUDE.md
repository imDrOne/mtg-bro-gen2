# CLAUDE.md — mcp-gateway

Гайд для Claude Code при работе внутри `services/mcp-gateway`. Общесистемный
контекст — в [docs/arch/](../../docs/arch/README.md), корневые правила — в
[корневом CLAUDE.md](../../CLAUDE.md).

## Назначение и границы

MCP-сервер — фасад над остальными сервисами системы для AI-агентов
(Claude, ChatGPT и т.п., подключаемых пользователем по URL). Предоставляет
tools, за каждым из которых стоит один или несколько gRPC-вызовов к
доменным сервисам. Обрабатывает OAuth2-редирект для MCP-клиента через
`authenticator`.

**Чем не владеет:** никакой собственной бизнес-логикой или данными — чистый
оркестрирующий слой. Не хранит карты, колоды, статьи, инсайты — только
проксирует и структурирует то, что вернули доменные сервисы.

## Данные

Нет собственной схемы БД. Может использовать Redis для короткоживущего кэша
MCP-сессия → токен (детали — по мере реализации в M6), но не для доменных
данных.

## Внешние зависимости

Нет прямых внешних API — только gRPC к внутренним сервисам и MCP-протокол
наружу к клиенту.

## Контракты

- MCP-протокол наружу — не REST, не gRPC. Список tools финализируется в M6,
  первая итерация — по кейсам из
  [data-flows.md, сценарий 3](../../docs/arch/data-flows.md#3-sealeddraft-через-mcp-по-фото-карт):
  `get_card_data`, `get_limited_stats`, `get_card_insights`, `save_deck`.
- gRPC-клиенты (внутрь): к `deck` (`CardService`, `DeckService`), к
  `limited-stats` (`StatsService`), к `insight-provider` (`InsightService`).
- Проверка токена MCP-сессии — через `libs/authx`, тот же механизм, что у
  остальных сервисов (не отдельная реализация).

## Внутренняя раскладка (ориентир для M6)

```
internal/
  tools/       # реализация каждого MCP tool
  clients/     # gRPC-клиенты к доменным сервисам, по одному на сервис
  session/     # привязка MCP-сессии к OAuth2-токену
```

## Принципы дизайна tools

- **Крупнозернистые, не микро-tools.** Один tool должен давать агенту
  самодостаточный ответ для принятия решения (например, `get_card_insights`
  возвращает и рейтинг, и комбо, и warnings одним вызовом — не заставляет
  агента делать три отдельных запроса и сшивать результат).
- Ответы — предсказуемо структурированные (стабильные ключи JSON), не
  вольный текст — агент должен уметь на них программно опираться.
- Ошибки от доменных сервисов транслируются в понятный агенту текст, не
  сырой gRPC-код.

Полный список и схемы tools — детально планируются позже, перед M6.

## Паттерны здесь

- **Circuit breaker** на каждый gRPC-клиент — падение одного доменного
  сервиса не должно вешать весь набор tools.
- Deadline propagation — MCP-запрос агента имеет свой таймаут, gRPC-вызовы
  наследуют его остаток, не независимые бесконечные контексты.

## Локальный запуск

```
task up
go run ./cmd/server
```

Нет `cmd/migrate` — сервис без собственной схемы БД.

## Метрики и алерты

RED-метрики по tool-вызовам (`mcp_tool_calls_total{tool,status}`,
`mcp_tool_duration_seconds{tool}`). Алерт на всплеск ошибок по конкретному
tool — сигнал, что доменный сервис за ним деградировал.

## Инварианты домена

- Ни один tool не выполняет действие от имени пользователя без валидного
  OAuth2-токена в MCP-сессии — не бывает «анонимных» tool-вызовов на запись
  (`save_deck` и подобные).
- Tool не должен успешно завершаться с частично применённым состоянием —
  если `save_deck` не смог сохранить полностью, агенту возвращается явная
  ошибка, не «наполовину сохранено, но 200 OK».

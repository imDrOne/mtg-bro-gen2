# Безопасность: OAuth2, JWKS, identity, секреты

## OAuth2-флоу

Два разных клиента, один authorization server (`authenticator`):

### Веб-фронт

Стандартный `authorization_code` + PKCE. Фронт — вне этого репозитория, но
контракт `authenticator` фиксируется уже сейчас в его `CLAUDE.md`, чтобы фронт
можно было писать параллельно.

### MCP-клиент (Claude, ChatGPT и т.п.)

- Пользователь подключает URL `mcp-gateway` в своём AI-клиенте.
- Первый вызов без валидного токена -> `mcp-gateway` отвечает 401 с
  `authorize_url`, ведущим на `authenticator`.
- Пользователь проходит login в браузере -> `authenticator` выдаёт
  `authorization_code` -> обмен на токен происходит по стандартному
  `authorization_code` + PKCE (тот же флоу, что у веба, разный `redirect_uri` и
  `client_id`).
- Токен привязывается к MCP-сессии; `mcp-gateway` прикладывает его к каждому
  исходящему gRPC-вызову.
- Выбор реализации (Ory Hydra vs своя на библиотеке) — открытый вопрос,
  [ADR-0008](adr/0008-oauth2-build-vs-buy.md). От выбора не зависит: сам
  flow, набор claims, `/.well-known/openid-configuration`, JWKS-эндпоинт.

## JWKS

- `authenticator` публикует `/.well-known/jwks.json`.
- Остальные сервисы верифицируют JWT **локально**, не ходят в `authenticator`
  на каждый запрос: `libs/authx` кэширует ключи по `kid`, обновляет по TTL и
  по алгоритму singleflight на промах кэша (чтобы при ротации ключа не
  случился одновременный шторм запросов к JWKS-эндпоинту от всех подов сразу).
- Ротация ключей: старый `kid` остаётся валидным для верификации некоторое
  окно после появления нового (grace period), чтобы токены, выданные до
  ротации, не инвалидировались резко.

## Identity в gRPC

- `mcp-gateway` и любой сервис, вызывающий другой сервис от имени
  пользователя, прокидывает исходный JWT в метаданных `authorization: Bearer <token>`.
- Принимающий сервис **сам** верифицирует токен через `libs/authx` — не
  доверяет утверждениям вызывающего сервиса без подписи. Сервис-к-сервису без
  пользовательского контекста (например, будущие фоновые задачи) —
  `client_credentials` с собственным `client_id` на сервис.

## Секреты

- Никаких секретов в репозитории. Локально — `.env`/`*.local*`
  (см. `.gitignore` в корневом `CLAUDE.md`), в проде — переменные окружения
  контейнера, инжектируемые на уровне docker compose prod (сам механизм
  раздачи секретов на проде — решается в рамках `deployment.md`/будущего
  CI, не блокирует эту документацию).
- Ключи LLM-вендоров существуют только в конфиге `insight-provider` — больше
  ни один сервис их не видит (соответствует [ADR-0007](adr/0007-embeddings-owned-by-insight-provider.md)).

## Парсеры: threat-заметки

- `limited-stats` и `article-parser` ходят на внешние ресурсы под контролем
  токен-бакета (`libs/httpx`) — не только вежливость к вендору, но и защита
  от случайного самопроизвольного DoS с нашей стороны при баге в шедулере.
- User-Agent парсеров — честный, с контактом/URL проекта, не маскируется под
  браузер.

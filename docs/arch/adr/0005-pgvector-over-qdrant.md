# ADR-0005: pgvector вместо отдельной векторной БД

## Статус

Accepted

## Контекст

`insight-provider` хранит эмбеддинги чанков статей для гибридного поиска,
используемого при формировании инсайтов и MCP-ответов. Нужно решить, где
жить векторам: в существующем Postgres или в специализированной векторной БД
(рассматривался Qdrant — удобный дашборд, богатая фильтрация по payload).
Сервер один и небольшой (бюджет ≤5к ₽/мес), лишний stateful-компонент имеет
реальную цену в RAM и в операционной сложности (ещё один бэкап, ещё один
мониторинг).

## Решение

Используем **pgvector** в том же Postgres-инстансе, отдельной схемой
(`insight`). Индекс HNSW.

Объём данных (эмбеддинги чанков статей с draftsim, порядок — десятки тысяч
записей) укладывается в pgvector с комфортным запасом. Гибридный поиск
(вектор + `tsvector` + фильтр по set/дате) выражается одним SQL-запросом
без похода в два разных хранилища и последующего join в коде.

Ручная проверка «что насобиралось» — через GoLand DB-тулинг и goland MCP
(`execute_sql_query`/`preview_table_data`) к тому же Postgres, отдельный UI
не нужен.

## Альтернативы

- **Qdrant отдельным контейнером.** Удобный `:6333/dashboard`, богатая
  фильтрация. Цена: ещё один stateful-компонент (+RAM, +бэкап), двойная
  запись (метаданные в Postgres, вектор в Qdrant) требует outbox/двухфазной
  синхронизации, чтобы не разъехаться — сложность не оправдана при текущем
  объёме данных.

## Критерии пересмотра

Возвращаемся к вопросу, если:

- объём эмбеддингов выйдет за десятки-сотни тысяч записей и HNSW-индекс в
  Postgres начнёт заметно давить на общий инстанс (влияя на `deck`/`auth`);
- понадобится фильтрация по payload существенно богаче, чем
  SQL `WHERE`-условия по индексируемым колонкам;
- появится нужда в multi-tenant изоляции векторов на уровне отдельного
  хранилища.

При пересмотре — `VectorStore` как Go-интерфейс в `insight-provider`
(зафиксировано в его `CLAUDE.md`) позволяет подменить реализацию без
переписывания вызывающего кода.

# ADR-0007: Эмбеддинги и весь LLM-доступ — в insight-provider

## Статус

Accepted

## Контекст

Есть два кандидата на то, чтобы считать эмбеддинги статей: `article-parser`
(источник текста) и `insight-provider` (уже вызывает LLM для структурированных
инсайтов). Нужно решить, где заканчивается ответственность парсера и
начинается ответственность AI-слоя.

## Решение

`insight-provider` — единственный владелец всех вызовов к LLM-вендорам, включая
эмбеддинги. `article-parser` занимается только парсингом: достаёт статью,
чистит текст, публикует `article.parsed` в Kafka и на этом останавливается.

Обоснование:

- Один набор API-ключей, один rate-limiter, один token-budget — вместо
  дублирования этой логики в двух сервисах.
- `article-parser` не должен тянуть зависимость на LLM SDK — его домен чисто
  «получить и сохранить текст», добавление LLM-вызовов размывает границу и
  дублирует retry/лимиты/ключи, которые уже есть в `insight-provider`.
- Чанкинг текста перед эмбеддингом — часть той же обработки, что и генерация
  структурированных инсайтов; логично, что оба шага видят один и тот же
  предобработанный текст в одном сервисе.

## Альтернативы

- **article-parser сам считает и хранит эмбеддинги.** Дублирует
  вендор-ключи/лимиты, размывает границу «парсер vs AI-слой».
- **Отдельный сервис knowledge-base только для векторного поиска.** Чище
  формально, но добавляет ещё один сервис к эксплуатации на слабом сервере
  без сегодняшней необходимости — тот же аргумент, что в
  [ADR-0006](0006-catalog-and-deck-in-one-service.md).

## Последствия

- `article-parser` не имеет доступа к LLM-ключам вообще — по умолчанию меньше
  поверхность утечки секретов (см. [security.md](../security.md)).
- Векторный поиск, используемый MCP-агентом и `deck`, всегда идёт через
  `insight-provider` gRPC — он же владеет `pgvector` ([ADR-0005](0005-pgvector-over-qdrant.md)).

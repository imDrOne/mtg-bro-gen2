# ADR-0002: gRPC внутри системы, REST+OpenAPI наружу

## Статус

Accepted

## Контекст

Нужен транспорт для межсервисных вызовов (`mcp-gateway → deck`, `mcp-gateway →
insight-provider` и т.д.) и отдельно — публичный API для веб/мобильного
фронта. Один из явных учебных приоритетов проекта — потренироваться с gRPC,
при этом внешняя поверхность должна оставаться простой для будущего фронта
(REST+Swagger привычнее, проще дебажить curl'ом).

## Решение

- Межсервисные вызовы — gRPC, контракты в `libs/proto`, генерация через buf.
- Публичная поверхность (веб/мобильный фронт, прямые интеграции) — REST с
  OpenAPI-спекой на сервис.
- MCP-клиент — ни то, ни другое: говорит с `mcp-gateway` по протоколу MCP.

## Альтернативы

- **REST везде.** Проще стартовать, но теряется тренировка gRPC-специфики
  (contract-first через proto, deadline propagation, interceptors,
  streaming при необходимости для будущих кейсов типа потокового импорта).
- **Kafka как основной транспорт даже для синхронных вызовов.** Не подходит:
  часть кейсов (получить карту по id для отображения в UI) принципиально
  синхронны и требуют быстрого ответа — Kafka здесь усложнение без выгоды.

## Последствия

- Каждый межсервисный контракт — версионируемый `.proto`, правило обратной
  совместимости зафиксировано в [api-contracts.md](../api-contracts.md).
- Появляется маппинг gRPC-код → HTTP-код там, где REST-слой оборачивает
  gRPC-вызов.
- `mcp-gateway` становится де-факто gRPC-клиентом ко всем сервисам — его
  `internal/` раскладка должна это отражать (по клиенту на сервис).

# ADR-0001: Multi-module раскладка через go.work

## Статус

Accepted

## Контекст

Монорепо будет содержать несколько независимо деплоящихся сервисов и
несколько общих библиотек. У сервисов со временем разойдутся зависимости
(например, только `insight-provider` тянет тяжёлый SDK LLM-вендора, только
`mcp-gateway` — MCP SDK) — и на практике важно тренироваться именно на
многомодульном Go-репо, это часть цели проекта.

## Решение

- Каждый `services/<name>` и `libs/<name>` — отдельный Go-модуль со своим
  `go.mod`.
- Корневой `go.work` объединяет все модули для локальной разработки
  (`go build ./...`/`go test ./...` внутри рабочего пространства видят все
  модули без `replace`-директив).
- `libs/*` версионируются git-тегами вида `libs/scryfall/v0.1.0` — сервисы
  подключают конкретную версию через `go.mod`, а не «последний коммит из
  монорепо».
- Инструментальный `go.mod` в корне (текущий, с golangci-lint/mockgen как
  tool-зависимостями) остаётся — это тулинг репозитория, не библиотека кода.

## Последствия

- Плюс: сервис тянет только свои зависимости — компактные Docker-образы, чистый
  `go.sum` на сервис, понятная граница «что от чего зависит».
- Плюс: реальная тренировка версионирования внутренних библиотек — то, что
  спрашивают в контексте монорепо на собеседованиях.
- Минус: обновление общей либы требует бампа версии в каждом
  потребителе — не подхватывается «само» при следующей сборке. Осознанный
  trade-off ради изоляции.
- `task build`/`task test`/`task lint` должны научиться обходить модули
  (`go work`-aware команды) — правится в M0.

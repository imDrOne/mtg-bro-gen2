# ADR-0003: Миграции — отдельное мини-приложение, не часть старта сервиса

## Статус

Accepted

## Контекст

Многие сервисы будут иметь собственную схему БД. Нужен предсказуемый и
безопасный способ накатывать миграции, совместимый с будущим CI-пайплайном
(build → run_migrations → deploy), без выполнения DDL от имени рантайм-роли
сервиса.

## Решение

- Каждый сервис несёт `cmd/migrate` — отдельный бинарник/образ, который
  применяет миграции и завершается (exit 0/1), не остаётся резидентным
  процессом.
- Рантайм сервиса (`cmd/server`) никогда не запускает `migrate up` сам при
  старте — миграции считаются применёнными до деплоя.
- CI-контракт: `build_migrations` (сборка `Dockerfile.migrate`) →
  `run_migrations` (запуск образа, блокирующий шаг) → `build` → `deploy`.
- Роли БД разделены: `<svc>_migrator` (DDL, используется только `cmd/migrate`)
  и `<svc>_app` (DML, используется рантаймом) — см. [persistence.md](../persistence.md#роли-и-гранты).

## Альтернативы

- **Миграции на старте сервиса.** Проще в моноспейс-деплое, но: несколько
  реплик сервиса при рестарте гонятся применить миграцию одновременно (нужен
  тот же advisory lock, но без выгоды отдельной джобы); DDL-права утекают в
  рантайм-образ; нельзя предсказуемо остановить деплой при провале миграции
  до того, как код уже подхватился.
- **Ручной DBA-процесс.** Не подходит — цель именно автоматизировать и
  потренировать паттерн для собеседований.

## Последствия

- +1 Dockerfile и +1 образ на сервис — принятая цена за безопасность и
  предсказуемость.
- `cmd/migrate` спроектирован под будущий CI с самого начала (M0), хотя сам
  пайплайн — отдельная итерация.
- Инструмент — `golang-migrate` (обоснование — [ADR-0004](0004-sqlc-plus-pgx.md) частично пересекается, но выбор инструмента миграций сам по себе не требует отдельного ADR: единственная реальная альтернатива, Atlas, избыточна для нужд проекта — декларативная схема и авто-diff не нужны при ручных SQL-миграциях).

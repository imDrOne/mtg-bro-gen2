# ADR-0008: OAuth2/OIDC — своя реализация или готовый сервер

## Статус

**Proposed** — решение отложено до начала M4, не блокирует M0–M3.

## Контекст

`authenticator` должен обслуживать два разных клиента (веб-фронт, MCP-клиент
через redirect-флоу), выдавать JWT, публиковать JWKS. Keycloak исключён явно
(слишком тяжёл для бюджета/цели проекта — учить Go, а не администрировать
Java-приложение). Остаются два реалистичных пути:

1. **Ory Hydra** — headless OAuth2/OIDC-сервер, своя login/consent UI
   пишется отдельно и обращается к Hydra по admin API. Легче Keycloak,
   сертифицированная реализация протокола.
2. **Своя реализация на Go** поверх библиотеки (`ory/fosite` или
   `go-oauth2/oauth2`) — полный контроль, максимум обучающей ценности,
   но и полная ответственность за корректность флоу (в OAuth2 легко
   ошибиться в деталях, которые не всплывают до продакшена).

## Что не меняется от выбора

Контракт наружу фиксирован независимо от реализации — можно проектировать
остальные сервисы уже сейчас:

- `authorization_code` + PKCE как основной флоу (веб и MCP);
- `client_credentials` для сервис-к-сервису без пользовательского контекста;
- `/.well-known/openid-configuration` + `/.well-known/jwks.json`;
- набор claims в JWT (минимум: `sub`, `exp`, `iat`, `scope`, `client_id`);
- `libs/authx` верифицирует токены по JWKS независимо от того, кто их выдал.

## Критерии решения (зафиксировать перед M4)

- Сколько реального времени готовы вложить в корректность протокола vs в
  бизнес-функции — библиотека Hydra снимает риск протокольных багов, своя
  реализация даёт больше учебной ценности за счёт риска и времени.
- Насколько критична строгая спека-совместимость для MCP-клиентов
  (некоторые AI-хосты валидируют discovery-документ строже, чем «просто
  работает») — если да, готовый сервер безопаснее.
- Ресурсный след Hydra (лёгкий контейнер + своя БД или общий Postgres) против
  нулевого доп. контейнера при своей реализации.

## Следующий шаг

Ревизия этого ADR — первая задача вехи M4, до написания кода
`authenticator`. Меняется статус на Accepted с зафиксированным решением и
обоснованием по критериям выше.

# ADR-0004: sqlc для статики, pgx для динамики

## Статус

Accepted

## Контекст

Нужен слой доступа к Postgres. Часть запросов статична и известна на этапе
разработки (получить карту по id, вставить колоду). Часть — принципиально
динамична: поиск карт с произвольным набором фильтров, гибридный поиск в
`insight-provider` (вектор + текст + фильтры поset/дате). Опыт с предыдущего
проекта (Liquibase на Java) показывает предпочтение прямому SQL без лишней
абстракции поверх него.

## Решение

- **sqlc** генерирует типизированный Go-код из `.sql`-файлов с запросами;
  источник схемы — папка `migrations/` сервиса напрямую (без отдельной копии
  DDL для генератора).
- **pgx** (`pgxpool`) — прямые вызовы для запросов, которые нельзя выразить
  статическим SQL-файлом с фиксированным набором параметров.
- Оба используют один и тот же пул соединений на сервис.

## Альтернативы

- **ORM (GORM и т.п.).** Прячет реальный SQL, что противоречит и предпочтению
  «явный SQL как в Liquibase-практике», и цели прокачать Go/SQL напрямую.
- **Только pgx везде, без sqlc.** Максимум контроля, но много бойлерплейта
  сканирования строк на статичных запросах — sqlc убирает именно это без
  потери прозрачности (сгенерированный код читаем и лежит в репо).
- **query-builder (squirrel) как основной слой.** Хорош для динамики, но
  избыточен для статичных запросов и добавляет второй стиль работы с SQL
  рядом со sqlc без необходимости. Squirrel остаётся кандидатом №1, если
  ручной pgx-код для динамики станет громоздким — решается по факту, не
  сейчас.

## Последствия

- Источник правды для схемы — один: SQL-миграции. `sqlc.yaml` на них и
  указывает.
- В сервисах с существенной динамикой (`deck`-поиск, `insight-provider`-поиск)
  будет заметный объём написанного вручную SQL через pgx — это осознанно,
  не технический долг.

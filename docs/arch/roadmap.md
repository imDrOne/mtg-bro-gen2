# Вехи реализации

Порядок диктуется зависимостями: библиотеки раньше сервисов, `deck` раньше
всего что от него читает карточные данные, `authenticator` — перед тем, как
защищать реальные эндпоинты (до этого — статический dev-токен и общий
middleware, не блокирующий разработку).

## M0 — фундамент

- `go.work` + мультимодульная раскладка (`libs/*`, `services/*`), каждый со
  своим `go.mod`.
- `libs/core` (config, slog, graceful shutdown, healthz/readyz, доменные ошибки).
- `libs/httpx` (retry+jitter, rate limiter, circuit breaker, singleflight).
- Taskfile обновлён под обход модулей (`go work` вместо одиночного `go.mod`).
- `go-arch-lint` — границы импортов между `internal/` пакетами и между
  `services/*`/`libs/*`.
- `docker-compose.local.yml`: Postgres+pgvector, Redis, Redpanda.
- Шаблон сервиса (`cmd/server`, `cmd/migrate`, структура `internal/`).
- Побочный фикс: `Taskfile.yml` таска `up` — флаг `-p` стоит после `up` в
  `docker compose -f docker-compose.local.yml up -d -p mtg-bro-gen2`, что
  невалидно (флаг проекта должен идти перед подкомандой); поправить при первом
  реальном использовании таски.

**Выходной критерий:** `task build && task test && task lint` зелёные на
пустом шаблоне сервиса, `task up` поднимает инфраструктуру.

## M1 — deck: справочник карт

- `libs/scryfall` SDK: bulk-data эндпоинты + поиск.
- Стриминговый импорт `default_cards` (файл — сотни МБ, читаем потоково, не в
  память целиком).
- Таблицы карт/выпусков в схеме `deck`, миграции, sqlc-запросы.
- REST + OpenAPI: поиск карт, получение по id.
- gRPC `CardService` для внутренних потребителей (mcp-gateway, будущий
  limited-stats для маппинга name -> id).

**Выходной критерий:** локальный импорт полного bulk-набора укладывается в
разумное время и память, поиск по имени/тексту работает.

## M2 — deck: колоды

- Правила форматов (лимиты копий, легальность по формату, синглтон для
  Commander) как явный слой валидации.
- Библиотека пользователя, CRUD колод.
- Импорт/экспорт: txt/csv/json, Moxfield, TCGPlayer-скан-формат.
- Outbox + публикация `deck.saved`.

**Выходной критерий:** можно собрать, провалидировать, сохранить и
экспортировать колоду end-to-end через REST.

## M3 — limited-stats

- Распределённый шедулер: задача = `(set, format)`, лизинг через
  `FOR UPDATE SKIP LOCKED`, TTL аренды, heartbeat.
- Конфигурация отслеживаемых выпусков — в БД, управляется через REST.
- Метрики job-прогонов + TG-алерты на старт/финиш/провал/пропущенный шедул.
- REST для получения статистики по карточкам.

**Выходной критерий:** несколько локальных инстансов сервиса делят задачи без
дублей, алерт долетает до TG на реальном прогоне.

## M4 — authenticator

- Закрыть [ADR-0008](adr/0008-oauth2-build-vs-buy.md) — выбор реализации.
- `authorization_code` + PKCE, JWKS-эндпоинт, `libs/authx`.
- Минимальная login-форма (единственный фронт-код в этом репо).
- Остальные сервисы переключаются со статического dev-токена на реальную
  верификацию через `libs/authx`.

**Выходной критерий:** веб-флоу логина работает end-to-end, JWKS отдаётся,
`deck`/`limited-stats` проверяют токены по-настоящему.

## M5 — article-parser + insight-provider

- `article-parser`: WordPress API draftsim, поиск по ключевым словам, raw +
  очищенный текст, outbox → `article.parsed`.
- `insight-provider`: консьюмер `article.parsed`, LLM-вызов со structured
  output (JSON Schema валидация), чанкинг, эмбеддинги, pgvector, гибридный
  поиск, публикация `insight.ready`.
- Token-budget leasing на LLM-вызовы.

**Выходной критерий:** статья с draftsim доходит до готового структурированного
инсайта в БД без ручного вмешательства, повторная публикация не дублирует
данные (идемпотентность подтверждена).

## M6 — mcp-gateway

- MCP-сервер, tools поверх gRPC остальных сервисов.
- OAuth2-флоу для MCP-клиента (redirect на `authenticator`).
- Первый набор tools по кейсам из [data-flows.md](data-flows.md#3-sealeddraft-через-mcp-по-фото-карт).

**Выходной критерий:** реальный MCP-клиент (Claude/ChatGPT) может пройти
авторизацию и получить данные о карте через tool-вызов.

## M7 — сквозная наблюдаемость

- OTel-трейсы через все сервисы (контекст уже прокидывается с M0 —
  подключение SDK без рефакторинга call chain'ов).
- Сборщик метрик (Prometheus/VictoriaMetrics) + дашборды.

**Выходной критерий:** один запрос пользователя трассируется от REST-входа до
всех затронутых сервисов в едином UI.

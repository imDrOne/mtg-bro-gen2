# PostgreSQL: схемы, роли, слой доступа, миграции

## Схема на сервис

Один инстанс Postgres (экономим ресурсы слабого сервера), каждый сервис
владеет отдельной **схемой**, не базой:

| Сервис | Схема |
|---|---|
| deck | `deck` |
| limited-stats | `limited_stats` |
| article-parser | `article` |
| insight-provider | `insight` (включая pgvector-таблицы) |
| authenticator | `auth` |

Ни один сервис не читает чужую схему напрямую. Межсервисный доступ к данным —
только через gRPC владельца. Это правило может быть пересмотрено для
конкретной пары сервисов отдельным ADR, если производительность потребует
иного — по умолчанию его нет.

## Роли и гранты

На схему заводятся две роли:

- `<svc>_migrator` — владелец схемы, полный DDL. Используется только
  `cmd/migrate`, никогда рантаймом сервиса.
- `<svc>_app` — гранты только на `SELECT/INSERT/UPDATE/DELETE` по таблицам
  схемы. Используется рантаймом сервиса.

Так компрометация или баг в сервисе не даёт `DROP TABLE`/`ALTER TABLE`.

## Слой доступа к БД: sqlc + pgx

- **sqlc** — для всех статических запросов. Источник схемы для sqlc — папка
  `migrations/` сервиса (`sqlc.yaml` указывает на неё напрямую, `.down.sql`
  sqlc игнорирует сам). Отдельной копии DDL для генерации нет — одна правда.
- **pgx** (`pgxpool`) напрямую — для запросов, которые физически не
  укладываются в статический SQL: динамические фильтры поиска карт,
  сортировки по нескольким полям на выбор пользователя, гибридный поиск в
  `insight-provider` (вектор + `tsvector` + произвольные фильтры).
- Если объём ручного `pgx`-кода начнёт разрастаться и терять читаемость,
  следующий шаг — `squirrel` поверх тех же соединений; отдельного ADR под это
  пока нет, конвенция — на будущее по факту.

## Миграционный паттерн

Каждый сервис несёт собственное мини-приложение миграций — код сервиса не
запускает миграции сам при старте.

```
services/<name>/
  cmd/
    server/main.go      # рантайм-приложение
    migrate/main.go     # мини-приложение миграций, отрабатывает и умирает
  migrations/
    000001_init.up.sql
    000001_init.down.sql
    ...
  Dockerfile             # для cmd/server
  Dockerfile.migrate      # для cmd/migrate
```

### Инструмент: `golang-migrate`

- Только голый SQL в `.up.sql`/`.down.sql` — без миграций, описанных Go-кодом.
- Файлы вшиваются в бинарник через `embed.FS` + драйвер
  `golang-migrate/source/iofs` — `cmd/migrate` не тянет файлы с диска в рантайме,
  весь набор миграций живёт внутри образа.
- `golang-migrate` сам берёт `pg_advisory_lock` на время применения — безопасно
  запускать джобу параллельно с нескольких раннеров/ретраев, гонки не будет.

### `cmd/migrate` — подкоманды

| Подкоманда | Назначение |
|---|---|
| `up` | накатить все непринятые миграции |
| `down` | откатить одну миграцию (ручной аварийный сценарий) |
| `version` | показать текущую версию схемы |
| `force <version>` | снять dirty-флаг после ручного вмешательства |
| `seed --env=<env>` | залить среда-специфичные данные (фикстуры, dev-пользователи) |

### Почему нет liquibase-style контекстов

В `golang-migrate` нет аналога liquibase-меток «выполнить только на среде X» —
и он не нужен: миграции описывают **схему**, а она одинакова на всех средах
без исключений. Всё, что раньше просилось в контекст (тестовые данные,
дефолтные админы для dev) — это не миграция, а **сид**, отдельная подкоманда
`seed`, которая не участвует в проде.

### Expand/contract

Миграции — только аддитивные в рамках одного релиза: добавить колонку/таблицу
можно и нужно до деплоя нового кода сервиса (`run_migrations` идёт до `deploy`
в пайплайне), а старая версия рантайма должна продолжать работать на новой
схеме. Удаление/переименование колонки — двумя релизами: сначала код
перестаёт её использовать, затем отдельная миграция дропает.

### Контракт CI-джоб

Сам пайплайн — отдельная итерация (не в этом плане), но контракт джоб фиксируем
уже сейчас, чтобы `cmd/migrate` проектировался под него:

```
build_migrations   # docker build -f Dockerfile.migrate
run_migrations     # docker run <migrate-image> up
build              # docker build -f Dockerfile (сервис)
deploy             # выкатка сервиса
```

`run_migrations` — блокирующий шаг перед `deploy`. Провал миграции = стоп
пайплайна, `deploy` не выполняется.

## pgvector

Живёт в схеме `insight`, расширение `CREATE EXTENSION IF NOT EXISTS vector`
ставится первой миграцией этой схемы. Индекс — HNSW, объём (десятки тысяч
чанков статей) укладывается без проблем в бюджет RAM слабого сервера.
Обоснование выбора pgvector вместо отдельной векторной БД — [ADR-0005](adr/0005-pgvector-over-qdrant.md).

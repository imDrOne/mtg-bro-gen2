# Kafka: топики, схемы, гарантии доставки

## Зачем вообще Kafka

Единственный сейчас настоящий асинхронный пайплайн — `article-parser → insight-provider`
и его выход дальше в консьюмеры. Остальные сервисы синхронны (gRPC) или вовсе
не общаются друг с другом. Kafka не вводится «про запас» — она нужна конкретно
для развязки парсинга статей и дорогих/медленных LLM-вызовов, и как шина,
через которую произвольные будущие консьюмеры подписываются на готовые инсайты
не трогая `insight-provider`.

## Реестр топиков

| Топик | Producer | Consumer(s) | Ключ партиционирования | Схема значения |
|---|---|---|---|---|
| `article.parsed` | article-parser | insight-provider | `article_id` | см. ниже |
| `insight.ready` | insight-provider | (будущие: deck — рекомендации, mcp-gateway — кэш) | `article_id` или `card_id` в зависимости от типа инсайта | см. ниже |
| `deck.saved` | deck | (будущие консьюмеры аналитики) | `deck_id` | см. ниже |

Ключ партиционирования всегда — идентификатор сущности, чтобы события одной
сущности обрабатывались строго по порядку одним консьюмером.

## Формат сообщения (конверт)

Все события — JSON с общим конвертом:

```json
{
  "event_id": "uuid",
  "event_type": "article.parsed.v1",
  "occurred_at": "2026-09-21T12:00:00Z",
  "idempotency_key": "uuid",
  "payload": { }
}
```

- `event_type` включает версию (`.v1`) — при breaking-изменении схемы заводим `.v2`, оба варианта живут, пока не выкатятся все консьюмеры.
- `idempotency_key` — то, что консьюмер использует для дедупликации (обычно совпадает с `event_id`, но может быть доменным, если продюсер физически не может гарантировать once-only на своей стороне).

### `article.parsed.v1`

```json
{
  "payload": {
    "article_id": "uuid",
    "source": "draftsim",
    "url": "https://draftsim.com/...",
    "title": "string",
    "set_code": "string|null",
    "cleaned_text": "string"
  }
}
```

### `insight.ready.v1`

```json
{
  "payload": {
    "insight_id": "uuid",
    "source_article_id": "uuid|null",
    "kind": "article_summary|card_rating|combo",
    "structured": { }
  }
}
```

### `deck.saved.v1`

```json
{
  "payload": {
    "deck_id": "uuid",
    "user_id": "uuid",
    "format": "commander|standard|draft|sealed|...",
    "card_count": 0
  }
}
```

## Гарантии доставки

- **At-least-once везде.** Ни один консьюмер не считает сообщение уникальным по факту получения — обязана быть дедупликация по `idempotency_key` (таблица `processed_events` с уникальным индексом либо upsert по бизнес-ключу).
- **Outbox на продюсере.** `article-parser` и `deck` пишут событие в таблицу `outbox` в той же транзакции, что и доменные данные; отдельный relay-процесс (из `libs/kafkax`) вычитывает `outbox` и публикует в Kafka, помечая строки отправленными. Так «запись в БД произошла, событие потерялось» невозможно.
- **DLQ.** Каждый топик `<name>` имеет `<name>.dlq`. Если обработка сообщения падает после N ретраев (конфигурируется, стартовое значение — 3 с backoff), сообщение уходит в DLQ с причиной ошибки в заголовке `x-error`. DLQ не блокирует партицию — обработка продолжается со следующего offset.
- **Retention.** 7 дней на всех топиках, кроме DLQ — там 30 дней (успеть разобрать руками).

## Локально

M0 разворачивает Redpanda (совместим с Kafka API, легче в RAM) в
`docker-compose.local.yml`. Прод — решается в [deployment.md](deployment.md), кандидат тот же Redpanda ради экономии ресурсов на слабом сервере.

# Паттерны распределённых систем: где и зачем

Одна из целей проекта — прокачать Go и паттерны, которые спрашивают на
собеседованиях. Правило: паттерн попадает в систему только если решает
реальную проблему **этой** системы — не ради тренировки саму по себе. Каждая
строка ниже отвечает на вопрос «какую конкретно проблему это решает здесь».

| Паттерн | Где | Реальная потребность |
|---|---|---|
| Token-bucket rate limiting | `libs/httpx`, используется клиентами Scryfall (~10 rps по ToS), 17lands, draftsim, LLM API | Прямое требование вендоров — превышение лимита грозит баном ключа/IP |
| Retry + exponential backoff + jitter | `libs/httpx` | Внешние API (особенно парсинг-источники) нестабильны, транзиентные ошибки — норма |
| Circuit breaker | Внутренние gRPC-клиенты и внешние HTTP-клиенты | Упавший источник (LLM-вендор, 17lands) не должен доводить вызывающий сервис до таймаутного каскада — быстрый fail вместо накопления зависших горутин |
| Singleflight | `deck` — параллельные промахи кэша по одной и той же карте при пиковой нагрузке; `libs/authx` — параллельная загрузка JWKS при истечении кэша | Дедупликация одновременных одинаковых запросов к БД/внешнему API |
| Cache-aside с TTL+jitter | Redis в `deck` (карточные данные) и `limited-stats` (статистика) | Классический read-heavy кейс; джиттер на TTL — чтобы много ключей не протухли одновременно и не создали dogpile |
| Outbox | `article-parser` (публикация `article.parsed`), `deck` (публикация `deck.saved`) | Атомарность «запись в БД + публикация события» без распределённой транзакции |
| Лизинг задач (`SELECT ... FOR UPDATE SKIP LOCKED`) | `limited-stats` — несколько инстансов парсера разбирают очередь `(set, format)` | Прямая потребность: распределённый шедулер, чтобы один и тот же выпуск не парсили дважды параллельно |
| Token/budget leasing | `insight-provider` — расход LLM API в рамках окна (день/месяц) | Бюджет ≤5к/мес реален и его легко превысить неконтролируемыми LLM-вызовами |
| Идемпотентность по ключу | Все Kafka-консьюмеры, импорт колод/библиотек | At-least-once доставка Kafka + повторные ручные импорты одного файла пользователем |
| Bounded worker pool / backpressure | Оба парсера при массовой обработке (сотни статей/сетов) | Слабый сервер — неограниченный параллелизм его уронит |
| Graceful shutdown + connection draining | Все сервисы, база в `libs/core` | Написать один раз правильно, а не на каждый сервис заново |
| DLQ | Все Kafka-консьюмеры | Poison-сообщение не должно стопорить партицию для остальных |

## Явно не берём (и почему)

- **Saga / распределённые транзакции.** Всё, что нужно от межсервисной
  консистентности здесь, покрывается outbox + идемпотентными консьюмерами;
  многошаговых бизнес-транзакций через несколько сервисов с компенсациями в
  системе нет.
- **Service mesh (Istio/Linkerd).** Оверинжиниринг для количества сервисов и
  ресурсов сервера; mTLS/трейсинг проще получить через `libs/authx`+OTel
  напрямую в коде.
- **k8s-операторы, StatefulSet-оркестрация.** Нет k8s вообще (см.
  [deployment.md](deployment.md)).
- **CQRS с раздельными read/write хранилищами.** Нагрузка не того порядка,
  чтобы читающая модель не успевала обслуживаться той же схемой.
- **Event sourcing.** Overkill для доменных моделей deck/colлекций — обычные
  таблицы с историей через `updated_at`/outbox-события достаточны.
